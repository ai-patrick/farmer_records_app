1· Lab Objective

The goal of this lab is to build an interactive Android screen that collects farmer record input (farmer name/reference, crop, and quantity in kg), validates each field, displays accepted records in a RecyclerView list with a live record count, and handles lifecycle events (launch, Home, return, rotation) correctly. By the end of this lab the app can:

⌨
Capture Input
Material TextInputLayout + TextInputEditText fields for farmer name, crop, and quantity with floating labels and built-in error text.
✅
Validate
Reject missing identity, blank crop, blank/negative/non-numeric/non-finite quantity. Zero is allowed (valid zero harvest event).
📋
List & Count
RecyclerView with adapter shows each accepted record; live count updates on every insert.
🔄
Lifecycle
Draft values survive rotation via onSaveInstanceState; records persist in-memory during process lifetime; process restart loses in-memory state (not persistent storage).

2· How the App Works

Before writing code, it helps to see the user journey. The app has a single screen with a form at the top and a live list below. The decision point: is the form valid?

        String draftQuantity = savedInstanceState.getString("draft_quantity", "");

        editTextQuantity.setText(draftQuantity);

    buttonSubmit.setOnClickListener(v -> onSubmit());

4.3 onSaveInstanceState(): Retaining Draft Values Across Rotation

Only the in-progress form fields are saved. The record list is NOT saved here — it lives in the Activity's heap and survives rotation because the Activity is recreated but the process stays alive. A process restart (swipe away from recents, then relaunch) loses this in-memory state; that is expected because we are not using persistent storage (Room, SharedPreferences, etc.) in this lab.

MainActivity.java · onSaveInstanceState
@Override
protected void onSaveInstanceState(Bundle outState) {
    super.onSaveInstanceState(outState);
    // Save draft values across rotation
    outState.putString("draft_farmer_name", editTextFarmerName.getText().toString());
    outState.putString("draft_crop", editTextCrop.getText().toString());
    outState.putString("draft_quantity", editTextQuantity.getText().toString());
}
⚠ Watch out. Do not describe in-memory state as persistent storage. The record list survives rotation because the process stays alive; it does not survive a process restart. Persistent storage would require a database (Room), SharedPreferences, or file I/O.

4.4 onSubmit(): Validation, List Update, Form Clear

Each field is cleared of old errors first, then checked. Validation rules:

Field Rule Error Message
Farmer Name / Reference Required (non-blank after trim) "Please enter farmer name or reference"
Crop Required (non-blank after trim) "Please enter crop name"
Quantity Required, numeric, finite, ≥ 0 "Please enter quantity in kg" / "Quantity must be a valid number" / "Quantity cannot be negative" / "Quantity must be a finite number"
💡 Zero is allowed. The earlier delivery exercise required a positive quantity; a zero weekly harvest is a different valid business event. We accept zero because a farmer may report no harvest for a week — that is a legitimate record, not an error.

On success: create FarmerRecord, insert at position 0 (top of list), notify adapter, scroll to top, update count, clear form fields.

MainActivity.java · onSubmit
private void onSubmit() {
    String farmerName = editTextFarmerName.getText().toString().trim();
    String crop = editTextCrop.getText().toString().trim();
    String quantityStr = editTextQuantity.getText().toString().trim();

    // Clear previous errors
    layoutFarmerName.setError(null);
    layoutCrop.setError(null);
    layoutQuantity.setError(null);

    boolean valid = true;

    // Validation 1: Farmer name / reference required
    if (TextUtils.isEmpty(farmerName)) {
        layoutFarmerName.setError("Please enter farmer name or reference");
        valid = false;
    }

    // Validation 2: Crop required
    if (TextUtils.isEmpty(crop)) {
        layoutCrop.setError("Please enter crop name");
        valid = false;
    }

    // Validation 3: Quantity required, numeric, non-negative, finite
    if (TextUtils.isEmpty(quantityStr)) {
        layoutQuantity.setError("Please enter quantity in kg");
        valid = false;
    } else {
        try {
            double quantity = Double.parseDouble(quantityStr);
            if (quantity < 0) {
                layoutQuantity.setError("Quantity cannot be negative");
                valid = false;
            } else if (!Double.isFinite(quantity)) {
                layoutQuantity.setError("Quantity must be a finite number");
                valid = false;
            }
            // Zero allowed — valid zero harvest event
        } catch (NumberFormatException e) {
            layoutQuantity.setError("Quantity must be a valid number");
            valid = false;
        }
    }

    if (!valid) {
        return;
    }

    // Create record and add to list
    double quantity = Double.parseDouble(quantityStr);
    FarmerRecord record = new FarmerRecord(farmerName, crop, quantity);
    recordList.add(0, record); // Add to top
    recordAdapter.notifyItemInserted(0);
    recyclerViewRecords.scrollToPosition(0);

    // Update record count
    textViewRecordCount.setText("Records: " + recordList.size());

    // Clear form
    editTextFarmerName.setText("");
    editTextCrop.setText("");
    editTextQuantity.setText("");
}

4.6 RecyclerView Adapter

Uses the platform's simple_list_item_2 layout (two TextViews) for simplicity. In a production app you'd use a custom layout.

MainActivity.java · RecordAdapter
// RecyclerView Adapter
private static class RecordAdapter extends RecyclerView.Adapter {
    private final List records;

    public RecordAdapter(List records) {
        this.records = records;
    }

    @Override
    public RecordViewHolder onCreateViewHolder(ViewGroup parent, int viewType) {
        View view = LayoutInflater.from(parent.getContext())
                .inflate(android.R.layout.simple_list_item_2, parent, false);
        return new RecordViewHolder(view);
    }

    @Override
    public void onBindViewHolder(RecordViewHolder holder, int position) {
        FarmerRecord record = records.get(position);
        holder.text1.setText(record.farmerName + " — " + record.crop);
        holder.text2.setText(String.format("%.2f kg", record.quantity));
    }

    @Override
    public int getItemCount() {
        return records.size();
    }

    static class RecordViewHolder extends RecyclerView.ViewHolder {
        TextView text1, text2;

        public RecordViewHolder(View itemView) {
            super(itemView);
            text1 = itemView.findViewById(android.R.id.text1);
            text2 = itemView.findViewById(android.R.id.text2);
            text1.setTextSize(16);
            text2.setTextSize(14);
        }
    }
}

7· Lifecycle Trace & Explanation

Predicted vs observed lifecycle sequence for each case:

Scenario Predicted Sequence Observed (Logcat) Explanation
Cold launch onCreate → onStart → onResume Matches Fresh process, no savedInstanceState
Rotation onPause → onStop → onDestroy → onCreate → onStart → onResume Matches Activity recreated; savedInstanceState non-null → draft restored
Home press onPause → onStop Matches Activity stopped, process alive
Return from Home onRestart → onStart → onResume Matches Activity restarted, no recreation
Process restart (swipe from recents) onPause → onStop → onDestroy → (process dies) → onCreate → onStart → onResume Matches New process, savedInstanceState is null → draft lost, list lost

What survives what?

  • Screen state (draft field values): saved in onSaveInstanceState → survives rotation, Home/return; does not survive process restart.
  • SavedInstanceState bundle: survives rotation and Home/return (process alive); does not survive process restart.
  • In-memory record list: survives rotation and Home/return (process alive); does not survive process restart.
  • Persistent storage (Room/SharedPreferences/files): would survive everything — not implemented in this lab.
⚠ Key distinction: A correct display (list shows records) does not prove a record is safely stored. The list is an in-memory ArrayList backed by the adapter. If the process is killed (low memory, user swipes away, crash), the data is gone. For MavunoLink, farmer records must be written to a local database (Room) and synced to the server — the UI list is just a view of that persisted data.

8· Design Choices, Defect Corrected, Limitation

Design Choice 1: In-memory list + RecyclerView (no database yet)

Reasoning: The lab focuses on input, validation, list display, and lifecycle — not persistence. Using an ArrayList + adapter keeps code minimal and makes the connection between input → model → adapter → visible list obvious. For MavunoLink, this would be replaced by a Room database with a DAO, and the RecyclerView would observe a LiveData/Flow from the DAO.

Design Choice 2: Validation in Activity (not ViewModel)

Reasoning: For a single-screen lab, putting validation in the Activity is pragmatic and readable. In MavunoLink, validation logic would live in a ViewModel or a dedicated validator class, unit-testable without Android context.

Defect Corrected: Quantity zero rejection

Original bug: Early version rejected zero (treated as invalid). Correction: Changed condition from quantity <= 0 to quantity < 0 and added explicit Double.isFinite check. Zero is a valid business event (zero weekly harvest) — different from the earlier delivery exercise which required positive quantity for a "delivery".

Limitation: No persistent storage

Records are lost on process restart. In MavunoLink, every accepted record must be written to Room immediately, and the RecyclerView should observe the database. This lab intentionally omits Room to isolate the form/validation/list/lifecycle learning objectives.

9· Relation to MavunoLink

  • Farmer identity: In MavunoLink, "Farmer Name / Reference" maps to a registered farmer ID (from the farmer registry). The app would validate against the local farmer cache or server.
  • Crop: Would be a spinner/dropdown populated from the crop master data, not free text.
  • Quantity: Server-side validation also applies (e.g., max plausible yield per acre). The client-side validation here is the first line of defense.
  • Record list: In MavunoLink, this is a synced offline-first list — Room + WorkManager sync to backend. The UI list is a projection of the local database.
  • Lifecycle: MavunoLink must handle background sync, network loss, and process death gracefully — ViewModel + SavedStateHandle + Room + WorkManager cover this.
